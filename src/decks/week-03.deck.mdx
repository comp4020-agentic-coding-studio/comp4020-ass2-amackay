## A verifier runs a stack

It reads a proof as a list of labels. Section 4.1.4 of the
[Metamath book](https://us.metamath.org/downloads/metamath.pdf) is the whole
rule.

```notes
One section, one data structure. Everything on the next slide is that section
in four lines, and the verifier project in week 5 is that section in code.
```

---

## The rule

- A hypothesis label pushes its expression
- An assertion label matches its hypotheses to the stack top by substitution,
  pops them, pushes the result
- At the end, one entry remains: the statement proved
- Every substitution respects `$d`

[Metamath book, section 4.1.4](https://us.metamath.org/downloads/metamath.pdf)

```notes
Push, match, pop, push. The only search a verifier does is finding the
substitution, and the proof has already told it which assertion to try.
```

"Metamath verifiers do not make logical inferences; they just verify that the
proof as stated is correct."

— [Metamath Home Page](https://us.metamath.org/index.html)

```notes
This is why the program is small and why there can be many of them. Nothing
is discovered; a claim is checked.
```

## Five verifiers gate set.mm

- [metamath.exe](https://github.com/metamath/metamath-exe), C, Norman Megill
- [checkmm](https://us.metamath.org/downloads/checkmm.cpp), C++, Eric Schmidt
- [smetamath-rs](https://github.com/sorear/smetamath-rs/blob/master/README.md),
  Rust, Stefan O'Rear
- [mmj2](https://github.com/digama0/mmj2), Java, Mel L. O'Cat and Mario Carneiro
- [mmverify.py](https://us.metamath.org/downloads/mmverify.py), Python, Raph Levien

[How are the databases verified?](https://github.com/metamath/set.mm/blob/develop/verifiers.md)

```notes
Every change to set.mm and iset.mm is re-verified by all five, the page says.
Five languages, five authors: a bug would have to be shared to let a bad
theorem through.
```

## The machinery

A GitHub Actions workflow,
[verifiers.yml](https://github.com/metamath/set.mm/blob/develop/.github/workflows/verifiers.yml),
run on every push and pull request.

Each job downloads, builds and runs one verifier.

```notes
Open the file and find the five jobs; that is one of this week's readings. It
is the concrete form of "re-verified by five different verifiers".
```

## checkmm, up close

- One `.cpp` file from
  [its author's repository](https://github.com/EricSchmidt-119/checkmm)
- Its header comment: every verifier would have to share a defect for an
  invalid theorem to get in
- It counts four verifiers; the prose page counts five

[checkmm.cpp](https://us.metamath.org/downloads/checkmm.cpp)

```notes
A whole verifier in one source file, and its own comment makes the
independence argument. The two sources disagree on the count; notice it, and
cite the one you use.
```

## Testing the testers: metamath-test

Databases that should and should not pass, with drivers for six verifiers.

Without the failing cases, "if you replaced a verifier with the program "true"
it would produce the same results".

[metamath-test README](https://github.com/david-a-wheeler/metamath-test/blob/master/README.md)

```notes
A verifier that accepts everything passes every positive test. The suite
exists for the proofs that must be rejected, and that is the reading for the
week.
```

---

## Testing the testers: mm-verifier-tests

Edge cases, each marked `$( should verify $)` or `$( should error $)`.

The verifier project, set in week 5, is run against both suites.

[mm-verifier-tests README](https://github.com/LegionMammal978/mm-verifier-tests/blob/main/README.md)

```notes
The second suite is the awkward corners of the specification. When your
project is marked, these two suites are what it is run over, so read the
markers now.
```
